# Hotel Front Desk Log

Generated by the CerebrumDev factory role runner.

## What this is

A standalone platform. Every capability runs in-process: handlers invoke
blocks that were vendored into `vendor/blocks/` at build time, through
`app/dispatch.py`. There is **no call back to a block store at runtime** — the
platform runs with the factory switched off (`P1`).

## Capabilities

- `record_check_in` — record a guest check-in (guest name, room number, timestamp)
- `list_todays_check_ins` — list the check-ins recorded for the current day

## Vendored blocks

- `database`
- `validation`
- `dashboard`

## Run it

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --reload      # GET /health -> 200; GET /v1/jobs -> kernel JDs
.venv/bin/python -m pytest tests -m "not pilot"   # factory code-phase gate
.venv/bin/python -m pytest tests                   # includes Store-backed @pytest.mark.pilot
# or: .venv/bin/python scripts/release_gate.py
```

Data lands in `$STORAGE_PATH/platform.db` (default `./data`), stdlib sqlite3.
Schema is Alembic (`alembic upgrade head` at deploy). `app/store.py` does not
`CREATE TABLE`.

## Kernel jobs and HTTP

`GET /v1/jobs` lists every kernel's job description. Distinctive surfaces:

| Kernel | Job | Agent | Routes |
|---|---|---|---|
| `COLLECTOR` | Binding surveyor | consult | `GET /v1/catalog` |
| `CLONER` | Block stocker | none | `GET /v1/inventory` |
| `WRITER` | Platform manufacturer | manufacture | `GET /v1/capabilities`, `POST /v1/{capability}`, `GET /v1/{capability}`, `GET /v1/{capability}/{id}`, `PUT /v1/{capability}/{id}`, `DELETE /v1/{capability}/{id}`, `POST /v1/work_queue`, `POST /v1/work_queue/{id}/process`, `GET /v1/work_queue` |
| `TESTER` | Acceptance inspector | none | `GET /v1/gates` |
| `STORE_MANAGER` | Store registrar | none | `GET /v1/provenance` |

These routes inspect the manufactured platform. They do not re-run the factory
and they do not execute the test suite (`GET /v1/gates` describes coverage only).

## Network posture

`P1` — Delivered platforms run in-process against vendored blocks; local/scripted OCR only; no Store URL, no cloud LLM, no Ollama, no outbound HTTP at runtime.

This value is factory-stamped. A coding-agent README cannot change it.

## Authentication and tenancy

One bearer token (`PLATFORM_TOKEN`, default `dev-local-token`) identifies one
principal. Capability writes require it (`POST /v1/<capability>` without one is
HTTP 401; missing fields and bad enums are HTTP 422).

The tenant is resolved from the authenticated principal (`app/tenancy.py`),
never from a client-supplied name: a request carrying `X-Tenant` that disagrees
with the principal is refused with HTTP 403. `GET /v1/tenancy` shows the binding.

## Answers, precedence and the corpus

| Surface | What it does |
|---|---|
| `GET /v1/precedence` | `precedence.v1` as data: 1 certified > 2 documents > 3 formulas > 4 procedures |
| `GET /v1/formulas` | the versioned formula registry (layer 3), evaluated in a whitelisted namespace |
| `POST /v1/corpus/documents` | ingest one document for the bound tenant (`source_kind`, `certified`) |
| `GET /v1/corpus/documents` | this tenant's documents only |
| `GET /v1/answers?q=...` | a grounded answer: winning source, per-claim labels and every divergence record |
| `GET /v1/llm` | what the answer adapter really is: offline and deterministic, no provider |

`app/retrieval.py` scores chunks with a deterministic keyword model, so an
answer can be reproduced and audited. `app/llm.py` never calls a provider: it
composes the reply from the corpus and the formula registry and hands the model
the winner rather than letting it choose. Every answered question is logged in
`answer_log` with its labels and divergences.

## Vendor slices (named, never stubbed)

This platform vendors three Store blocks and binds all three:

| Block | Used by | Action |
|---|---|---|
| `database` | both capabilities | `insert` (the check-in row), `query` (today's rows) |
| `validation` | `record_check_in` | `validate_pipeline` (5-stage item validation) |
| `dashboard` | `list_todays_check_ins` | `render` (the front-desk list) |

Every one loads and executes offline; `app/vendor_health.py` probes them per
request and `GET /v1/vendor_health` reports the result. `KNOWN_DEFECTS` is
empty for this checkout and `docs/blockers.json` records no blocker. A block
that cannot run is named there and never stubbed into a passing call.

`vendor/**` is sealed and read-only for this build, so no vendored block is
patched here. The two `handle()` bodies are real: every declared block is
invoked with an `action=` keyword (never inside the payload), every block
input is constructed in the handler, and a block refusal fails the capability
closed instead of being reported as success.
